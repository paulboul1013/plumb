# Bug lane

A reported defect. Every shipped line traces to runtime evidence. A change that "might help" is a hypothesis, not a fix, and it does not ship.

1. **Diagnose.** Run `diagnose`. No hypothesis before one command goes red on the user's exact symptom.
2. **Re-classify.** Now that the cause is known, score size and the three doors again. A cause that crosses module boundaries raises the rigor. Score size by the modules the cause and the fix reach, never by the lines the patch changes: a one-line fix can still be M. When the fix touches code that enforces a data-integrity or security invariant, such as a uniqueness or once-only check, an atomic eligibility guard, a transaction boundary, deduplication, a balance, or an access check, score the change door one-way even when the fix keeps the invariant. Bad data or a leak that the bug lets through stays after a revert, and one-way sets the rigor to Standard or above, so a reviewer other than the writer checks the fix. Print the new line.
3. **Fix at the root.** Fix where the cause lives: the first place the system did something it should not, or failed to handle a state it should. The symptom is only where the wrong state became visible. Ask whether the state that triggered it is legitimate. If the system may be in that state, the code that broke on it is the root cause, and handling the state there is the fix. If the state should never exist, a guard, retry, swallowed error, or clamped value where it broke hides the bug, so find what produced the state. If the fix crosses a function boundary, or changes a concurrency, transaction, or routing contract even inside one function, run `design` first.

   **Blast radius of a shared mechanism.** When the fix routes a new caller through a mechanism other code already uses (a cleanup stack, an exit path, a cache, a lock), or makes it reachable from a place it could not run before, check what else that reach can break before you lock it in. Name the facts the mechanism assumes about its state when it runs, such as "every entry on the stack is ready to run", and prove each one at the new place with a small program instead of reading the code. Change what the new caller produces and where its result goes as well as where it sits: assign the result to a value that needs cleanup, store it in a field, pass it on. A fact that fails there is a bug the fix exposed. Fix it in this change only when the fix caused it; otherwise record it. When the fix changes behavior that another part of the system decides, such as a checker or a second backend, and that part disagrees, keep the old behavior and record the disagreement.
4. **Lock it.** Land the regression test before the fix in history when a correct seam exists. If no correct seam exists, write that down as a finding for `/plumb:retro`.
5. **Prove.** Re-run the original, un-minimised loop from step 1 and show red then green.
6. **Review.** Run `review` with the bug report as the spec.
7. **Deliver.** Run `deliver`. The PR body names the hypothesis that turned out true.

**Reply.** What was broken, the root cause, the fix, and the failing-then-passing output pasted verbatim. When the task publishes or deploys the fix, report separately what was fixed and verified, what was published, and what version and behavior the live runtime actually serves. A deployed fix without evidence from the live runtime leaves the bug open.
